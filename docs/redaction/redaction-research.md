# How real redaction tools treat vector line art, images and partly-covered text

Researched 2026-10-02. Sources: vendor documentation, vendor forum staff replies, open-source code (MuPDF master, Stirling-PDF main), local install files (LibreOffice 25.8 help, PDF24 toolbox), and one reproducible PyMuPDF test run on this machine. Where no source says what happens, the cell says **unknown**. Nothing below is a guess presented as fact; inferences are labelled.

### Local verification of MuPDF semantics (PyMuPDF 1.27.2.3 / MuPDF 1.27.2 on this machine)

Test page: a line from x=50 to x=500 crossing a box at x=200..300; a short line wholly inside the box; the text "SECRETTEXT partly" starting left of the box.

| graphics= | crossing line | inside line | text left |
|---|---|---|---|
| 0 NONE | kept, full length (still continuous under the black box) | kept | `SECRET` |
| 1 REMOVE_IF_COVERED (default) | **kept, full length** | removed | `SECRET` |
| 2 REMOVE_IF_TOUCHED | **removed entirely, including x=50..200 and 300..500** | removed | `SECRET` |

The test used 1.27.2. The app runs 1.28.2. The 1.28 changelog fix (#4936, "incomplete redaction of vector graphics (line art)") made redaction catch drawings it had been missing, such as invisible or clipped ones. The `culler` code on MuPDF master still works on bbox and per-subpath granularity and has no clipping, so the table above should still hold on 1.28.2.

**Documentation defect:** the PyMuPDF docs describe the two modes the wrong way round. They say `REMOVE_IF_COVERED` "removes any overlapping vector graphics" and `REMOVE_IF_TOUCHED` "removes graphics fully contained". MuPDF's code (`pdf-clean.c` `culler`: COVERED → `rect_touches_redactions(...) == 2`, i.e. fully inside; TOUCHED → `!= 0`, i.e. any overlap) and the local test both show the reverse. Code that relies on the doc text will get the opposite behaviour.

## Patterns

1. **Clip at the box edge** (geometric subtraction). The covered part of a path, glyph or image is deleted and the rest stays vector or pixels: **Adobe Acrobat** (documented default), **PDF-XChange Editor** (partly covered glyphs become shape fragments), **Apryse Redactor** (documented). This is the only pattern that keeps a table rule or signature stroke looking right on both sides of the box while leaving nothing under it.
2. **Whole-object decision by bounding box** (keep whole or remove whole). **MuPDF/PyMuPDF**, per subpath. Its default (`REMOVE_IF_COVERED`) keeps any partly covered stroke **intact under the black box**. The hidden part is still in the content stream and can be extracted (e.g. a signature or handwriting stroke that crosses the box edge). `REMOVE_IF_TOUCHED` closes that leak but deletes visible line art outside the box: table borders vanish, underlines disappear, chart axes break. Text is always handled as whole glyphs (any overlap removes the glyph). Images get pixel-level blanking by default.
3. **Rasterise the page**: **LibreOffice Draw** Redacted Export (always), **PDF24** Blacken (always), **Stirling-PDF** with "Convert PDF to image" (opt-in, off by default). PETS 2023 found Acrobat 21.5's default flow behaving this way too. It is safe for every content type, but the page loses text and vector quality, and the paper shows the raster width of the redacted text can still leak.
4. **Leave line art in place**: **Nitro PDF Pro** (documented: redaction touches only text and images; vector graphics must be deleted by hand). **Stirling-PDF** manual area mode without rasterisation leaves *everything* in place under an opaque rectangle.
5. **Unknown / undocumented**: Foxit (partial paths), macOS Preview, Bluebeam Revu (vectors), Smallpdf, iLovePDF.

Defaults in short: Acrobat, PDF-XChange and Apryse clip. MuPDF/PyMuPDF keeps partly covered subpaths whole by default. LibreOffice and PDF24 rasterise. Nitro leaves vectors. Stirling's area mode only overlays unless the user opts in to rasterising.

## Documented real-world failures

- **Glyph-position leakage after "proper" redaction.** Bland, Iyer and Levchenko (PoPETs 2023) deredacted hundreds of real redactions, including US OIG investigation reports and FOIA responses. Tools that remove the text but keep the surrounding glyph positions and shifts were attacked (Acrobat with postponed save, Foxit 11, Nitro 13, PDFelement, Qoppa). Rasterising tools still leaked the raster width. Two CVEs resulted (CVE-2022-30350, CVE-2022-30351), and the US Courts, DOJ and 22 agencies were notified. This is the partly-covered failure mode: what sits *around* the box encodes what was removed. https://petsymposium.org/popets/2023/popets-2023-0069.pdf
- **Overlay-only redaction:** the Paul Manafort filing (January 2019). Black bars were drawn over text that stayed in the file and could be copied out. Cited in Perkins Coie's "When Redactions Don't Redact": https://perkinscoie.com/insights/update/when-redactions-dont-redact . This is the same failure class as Stirling-PDF's non-rasterised area mode and Nitro's treatment of vectors.
- **Vector content specifically:** I found no documented court or government failure where *line art* (as opposed to text) survived under a box. The nearest documented cases are the macOS Preview vector-corruption report above and PyMuPDF issue #4936 (drawings surviving `apply_redactions(graphics=2)` in 1.27.1, fixed in 1.28.0): https://github.com/pymupdf/PyMuPDF/issues/4936
